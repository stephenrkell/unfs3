# NFS protocol lab

This is the documentation for the 6CCS3DSM lab session exploring the NFS protocol using Wireshark.

We will use unfs3, the userspace NFS server, whose source is in this repository. The upstream unfs3 README is in README.upstream.md.

You will need access to a Linux lab machine, or other Linux machine with Wireshark installed (and configured to allow your user account to capture packets).

# 0. Getting hold of unfs

Clone this repository on your working machine. You've already got the source!

You can build `unfs` from source, but that can be tricky as it has a few dependencies not found on
the lab machines (but easily installed if using your own machine). See README.upstream.md if
interested in doing this. Or from a lab machine, you can instead use a pre-built binary that I
provide... from your working directory, do:

```
make run
```

and you should see unfs3 starting up, using this pre-built binary. It will use (and print out) a
command like something like this:

```
/path/to/unfs3/unfsd -p -u -d -n 4711 -m 4711 -e /path/to/unfs3/exports
```

... where `-p` means skipping the `rpcbind` service (not important for us), `-n` and `-m` set the
TCP port numbers for the `mountd` and `nfsd` services respectively, and `-e` sets the exports file
to one that was created during the build process.

The `make run` will start the server in the background, so you can keep using your shell.

For test purposes, if you do not create your own `exports` file (in the same `unfs3` directory) the
makefile will create one for you that serves a local temporary directory, initially empty, over NFS.
If you run your own build of `unfs3` you will have to create this `exports` file yourself and pick
one or more directories for it to export. Either way, you should inspect this file: it defines which
part(s) of the host system's filesystem should be exposed over NFS. Feel free to edit it if you would like to serve a different part of your filesystem.

# 1. Getting hold of a Linux machine (emulated if need be) that can mount the NFS filesystem

To mount an NFS filesystem requires root privilege. If you are running on your own machine,
you will have root privilege already and can skip this step as long as you know what you are doing
(remember that what you do is your responsibility!).

If you are using a lab machine, you will have to use an emulated Linux machine on which you will
have root privilege. This will be able to mount the NFS filesystem served from your lab machine,
using the emulated networking in Qemu. Again, I have provided a pre-built binary of Qemu for
convenience, and a disk image for it to boot. If you do

```
make boot-qemu
```

you should get a serial console on this emulated Linux machine as it starts up.

This emulated machine is also configured to log the network traffic to a file called `netdump.pcap`.

Some practicalities for using the emulated machine:

* to log in, use username `root`, password `root`
* to quit, use Ctrl+A then X
* ... ideally after cleanly shutting down the emulated machine with `halt`
* you may want to run `reset` from your shell after quitting Qemu, if your terminal behaves strangely

# 2. Start Wireshark

In a terminal, run `wireshark`. (If you are using your own machine you may have to install the `wireshark` package.)

Select the loopback interface ('lo') from the list of interfaces, and press the blue 'capture' button.

This can be finnicky... some lab machines may not be configured to allow packet capture. If this affects you, the fallback is to load the packet trace generated by Qemu (File, Open) and re-load it on every interaction with the NFS filesystem (File, Open Recent).

Enter `nfs` in the filter line (below the toolbar).

# 3. Mount the NFS filesystem

We started a running NFS server (unfsd) above, but we've yet to do anything with it. We want to look at the network traffic. We'll start with just what happens when mounting the filesystem.

From your own machine or the emulated machine (but it won't work from a lab machine),
mount the NFS filesystem using a command like the following.

mount -t nfs -o port=4711,mountport=4711,mountvers=3,nfsvers=3,nolock,tcp 10.0.2.2:/NFSDIR /mnt

but you will have to

* if using your own machine, replace 10.0.2.2 with localhost
* replace `/NFSDIR` with the directory that was named in your `exports` file (perhaps resembling `/tmp/tmp.XXXXXXX` if you let the makefile generate this for you)

If this succeeds, you will have an NFS filesystem mounted at `/mnt` and can start to interact with it: use `ls` to list it (it should be empty), use `nano` to put a simple hello-world text file there, etc.

# 4. Examining the activity in Wireshark

You should see packets being captured by Wireshark. Remember to put `nfs` in the filter line to see
only NFS traffic. (And remember the workaround if needed on lab machines:  reload the `netdump.pcap`
file that Qemu has generated, every time you do a new interaction with the NFS server -- using the
'File -> Open Recent' menu option. This was not needed on a test run I did, but am supplying it out
of caution.)

# 5. Experimenting with the NFS protocol.

From here on, your task is, in general terms, to look at the NFS calls you see being captured as you perform various activity in the emulated machine, and explore their contents in Wireshark.

In the initial capture during mounting, you should see a response indicating that a particular
operation is unsupported. Which one? Using the NFS RFCs (linked in the lecture slides), look up what
this operation does and guess why it might not be supported.

Use the `ls` command to list the mounted directory and check back for the new activity captured by
Wireshark.

Can you see a file handle being passed? Using the `stat` command on the host machine, see if you can find how the relevant device and inode numbers are reflected in the file handle being passed.

You should be able to find an `ACCESS` call in the NFS traffic already captured. How does it represent file permissions? Why does it say "access denied" but still return with status "NFS3_OK"?

Create a test file through the NFS mount, and ensure you have written some contents to it. Check you
can see the write messages. Which field makes them idempotent?

Try restarting the server, without remounting. Does everything work as expected?

Use `stat` on a test file in the NFS mount. Repeat the `stat` a few seconds later. What can you infer about the caching of metadata on the client?

Use `cat` to read a test file in the NFS mount. Repeat the same `cat` a few seconds later. What can
you infer about the caching of file data on the client?
